# English and French

The site is written in English and speaks French on request. A switch on every
page turns the page over; nothing else about the site changes.

English is the source language and is never rewritten. Every page still ships its
English words in its own markup, exactly as before. `i18n.js` lays French over
the top when a visitor asks for it, remembering what it covered so that switching
back puts the original nodes straight back. The English site is the untouched
site: a rendered comparison, page by page, shows every English string identical
to what it was before French existed.

## The two files

| File | What it holds |
|---|---|
| `i18n.js` | The machinery. Knows no French. ~250 lines, no dependencies. |
| `i18n-fr.js` | Every French word on the site. Hand it to a translator on its own. |

A third language is one more `i18n-<code>.js` calling `MH_I18N.register()`. Nothing
in `i18n.js` needs to change.

## How a page gets the switch

Most pages load the pair themselves, in the head, before anything else:

```html
<script src="i18n.js"></script>
<script src="i18n-fr.js"></script>
```

Not deferred, on purpose: the tool pages run their own scripts while the document
parses and ask `MH_I18N` for their words on the way, and a blocking pair this
small also spares a French visitor a flash of English.

`menubar.js` injects the pair into any page that forgets. That is the safety net
for `Horrigan_CV.html`, whose markup is generated by the CV builder in
`storage/JOBMARKET/ClaudeDesigns` and would lose a hand-added script tag on the
next build. The CV's own controls are translated by selector for the same reason:
nothing in that file is hand-edited.

The switch mounts into the shared menubar where there is one, so it inherits the
bar's styling. On a page without a menubar (the walkable homepage, the Autofac
poster) it mounts as `#mh-lang`, a fixed pill a page can restyle: `autofac.html`
does, in its own idiom.

## Which language a visitor gets

`?lang=fr` in the URL wins, then the visitor's remembered choice
(`localStorage`), then English. **A browser set to French is not enough on its
own.** Nobody is moved off the English site without asking, and using the switch
rewrites the URL, so a French link is shareable.

## Links follow the language

While French is on, every same-site page link on the page carries `?lang=fr`
(`about.html?menu=Music` becomes `about.html?menu=Music&lang=fr`), and the world's
kiosks open their pages through `MH_I18N.href(url)`, which does the same. So the
next page opens in French whatever the browser does with storage: Safari, for
one, keeps a separate `localStorage` per `file://` document. External links,
anchors, and non-page files (the CV's PDF) are left alone, and switching back to
English restores every link exactly.

Two consequences for anyone writing rules or pages:

- Select a link by **prefix**, `a[href^="about.html"]`, never by exact `href`,
  or the rule stops matching the moment the suffix is added.
- Script code that opens a same-site page should pass the URL through
  `MH_I18N.href()` first (see `openPage` in `engine.js`).

## Adding or changing a string

**Words already in a page's markup** get a rule in `i18n-fr.js`, under that
page's file name (`"*"` means every page):

```js
{ sel: "#btn-print", text: "Imprimer les porte-noms" }
{ sel: ".lede", html: "… avec un <span class=\"hl\">lien</span> dedans" }
{ sel: "#max-mcq", attr: { placeholder: "toutes" } }
{ sel: ".setup-label", each: ["Régler la durée", "Sonneries aux moments clés"] }
```

`each` / `eachHtml` hand one string to each match in document order; `null` skips
one. Prefer a selector anchored on an id over a positional `each` wherever a
script rebuilds that part of the page, or the positions shift under you.

`textNode` replaces only the element's first run of text and leaves its child
elements alone: the words beside an `<input>` inside a `<label>`, for instance.

`late: true` marks chrome a script builds on demand (the Musebot selector appears
the first time a tower is placed). `i18n.js` watches the body for new top-level
elements and translates inside each as it lands, and `check()` does not report a
`late` rule as stale while its chrome is absent.

**Do not let two rules touch the same region.** A rule that replaces a block
snapshots whatever is inside it at that moment, so an inner rule that ran first
would be captured as if it were the English original, and switching back would
leave half the block translated.

**Words a script writes** call `say()` (or `MH_I18N.t()` in `engine.js`, `tr()`):

```js
setStatus(say("mcq.reading", "Reading questions…"), "info");
say("plates.loaded", "{n} names loaded from a {kind}.", { n: 12, kind: kind });
```

The English text is both the source and the fallback, so a missing translation
degrades to the English the page always had. Placeholders are filled in either
language.

**Words a script writes that must survive a switch** use `sayIn()`, which
remembers the element and repaints it:

```js
sayIn(statusRoster, "plates.loaded", "{n} names loaded…", { n: 12 });
```

Anything else that needs redrawing listens for the switch:

```js
document.addEventListener("mh:lang", renderRules);
```

**Words a skin draws onto the canvas** go through `U.tr()`, the same helper on
the `util` object every theme already receives (`theme-technocute.js` draws its
`ENTER →` prompt that way).

## What is not translated, on purpose

Names of things: the tools (MCQer, SeatPlanner, ExamTimer, Nameplates), the works
(Autofac: Rad Shipping, Rock Walls and Damp, No Phenomenon), the skins
(bureaucore, technurture, gloomthmaxx), titles of talks and papers, and the Canvas
column headings a teacher has to match by eye in an export. A name is an address,
not a description. MCQer's `[Question.]` / `[Answer.]` tags are input syntax, so
they are keywords too: only the prose around them is translated.

The Musebot selector is a special case. Its frame (title, help line, search
label, buttons) is translated by `late` rules. The bots' names and one-line
descriptions inside it are content from the `web-musebots` project, shipped in
the generated `signal-towers.js`, and stay as that project wrote them; a French
version of those belongs in the bundle's source, not here.

Further deliberate gaps:

- **The CV's contents.** `Horrigan_CV.html` is built from `src/cv.md` by the
  builder in `storage/JOBMARKET/ClaudeDesigns`, so a French CV means a French
  source and a builder that can emit both. Its menubar and its Web / Print / PDF
  controls are in French already.
- **`Rock_Walls_and_Damp.html`.** A 35-passage SugarCube hypertext whose links are
  part of its prose. That is literary translation, not localization.
- `Nameplates` and `SeatPlanner` keep their English default flag terms
  (`integrity concern`), because those are matched against the words in a
  teacher's own gradebook, not shown as prose.

## Inclusive French

`i18n-fr.js` states the conventions in full at the top of the file. In short:
neutral by construction first (`la population étudiante`, `les personnes qui
enseignent`, `spécialiste de la communication`); no generic masculine; `iel` /
`iels` as the pronoun where one is needed; the feminine first in a doublet, with
the accord de proximité; and no point médian, because screen readers read it out
as punctuation and this site spends its effort on being legible. The author's own
lines take no gender that has not been stated.

The house writing style (`brand/house-style.md`) governs the English. French keeps
French punctuation, including the non-breaking space before `: ; ! ?`, written as
` ` so it stays visible in the source.

## Checking it

```sh
python3 tools/i18n-check.py              # every page, both languages
python3 tools/i18n-check.py ExamTimer.html
```

It serves the repo, loads each page in headless Chrome, and reports: the switch is
present in both languages, `<html lang>` flips, **every French rule still matches
something**, and which visible strings are byte-identical in both languages. That
last list is a heuristic to read, not to obey: names and numbers are supposed to
match.

In a browser console, `MH_I18N.check()` reports the same rule coverage for the page
you are on. A stale rule scoped to that page is the one to fix; a stale `"*"` rule
just belongs to some other page's chrome.

`python3 tools/i18n-extract.py <page>` lists a page's reader-facing strings
(markup, attributes, and script literals), which is how to find what a new page
still needs.
